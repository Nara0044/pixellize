For agentic SRE, the question is not really build versus buy. It is which parts of the work are specific to your company, and which parts are the same for everyone.

This post is for teams that have already started building. You have a Slack bot that answers questions about alerts, a rightsizing job that runs on a schedule, maybe a few auto-remediation scripts. You are not going to throw that away, and you should not. This is a guide to keeping what you built and swapping the undifferentiated core underneath it for NudgeBee's open-source platform, so the full-stack operation you set out to build actually gets finished.

If you have read the two companion posts, the seven pitfalls of building from scratch and the seven gaps of relying on a general assistant, this is the constructive answer to both. If you have not, each section stands on its own.

Decide what is core and what is edge

One test sorts every component of an in-house agentic ops build: could another company run this unchanged? If yes, it is core. If no, it is edge.

Edge is your runbooks, your service knowledge, the SOP that says a payments incident pages two teams, the approval policy that lets staging self-heal but keeps production on human review, the model gateway you standardised on, and the specific workflows your on-call engineers have learned to trust. Nobody can build this for you, and it is the only part of the system that is actually yours.

Core is the always-on orchestrator, the structured memory and service dependency graph, model routing and the certified model list, the integration layer for Prometheus, New Relic, Datadog, GitHub, Slack and the cloud APIs, role-based access, audit trails, approval gates, egress scanning, spend budgets, and the maintenance of all of it through every model release and every Kubernetes version. It is the same in every company, it is most of the engineering effort, and it is where in-house builds stall.

The approach that works: keep building the edge, adopt the core, and treat the boundary between them as an API you contribute to rather than a system you own.

Bottom line: your team's time on the core is time no competitor sees and no customer values. Your team's time on the edge is the whole point.

What NudgeBee OSS gives you on day one

The open-source platform is the core, installed. Each item below is one of the seven pitfalls from the companion post, closed.

  • Always-on orchestration, not a chat loop. Agents run as standing workers with schedules, durable state, per-environment autonomy levels, budgets and a kill switch. Slack, Teams, CLI and web UI are interfaces onto that, not the engine.
  • b-Cortex memory and dependency graph. Structured memory scoped to tenant, application, environment, agent and session, plus a service dependency graph built deterministically from traces and platform metadata. Every investigation starts from what is already known.
  • Model routing and compatibility. Agents are tiered as reasoning, retrieval or summary and mapped to models accordingly. Any OpenAI-compatible endpoint, including your own gateway, plugs in. The project tracks model releases so your team does not re-test every agent.
  • One substrate, several functions. SRE, FinOps, Kubernetes ops and an automation builder ship together and share integrations, memory and the approval path. Your second function is a workflow, not a second project.
  • Governance from the first commit. RBAC, an audit trail of every command executed and evidence consulted, approval gates per environment, egress scanning of prompts for credentials.
  • Cost that stays flat. Small and open-weight models on high-volume steps, precise context from memory instead of log dumps, per-agent daily budgets and rate limits.
  • A maintained core. Integrations, model compatibility and security patches arrive with each release instead of with your two platform engineers' spare time.

The unit of execution is a tightly scoped task worker agent. One job, a fixed set of actions, pointed only at the clusters or accounts you give it, behind the policy gate. This is what makes autonomous action in production reviewable: security approves a worker once, by its scope and action types, not every action it might take. These task worker agents (NudgeBee calls them Worker Bees) ship in the open-source core, along with the guardrail framework: scope, action types, trust dials per environment, approval and rollback. Why a tightly scoped task worker is the safest way to run execution actions in production is the subject of a companion post.

What you still build

Everything that makes the system yours, and none of it is throwaway.

  • Workflows. Your rightsizing logic, your alert handling, your remediation scripts, expressed as NudgeBee workflows: YAML or no-code, with webhook, schedule, event and lifecycle triggers, mixing deterministic steps (a script, a container) with LLM steps where judgement is needed. They version in Git and deploy through your CI/CD.
  • Custom agents. Agents for the things only your estate has: a legacy batch system, a bespoke deployment pipeline, a compliance check regulators ask about. Built in the same builder the shipped agents use.
  • Knowledge. Runbooks, Confluence spaces, past incident write-ups, service ownership. Loaded once into b-Cortex and reused by every agent.
  • Internal tools as MCP servers. Anything with an API inside your network, exposed to agents through the Model Context Protocol so they can call it like any other tool.
  • Policy. Which environments allow autonomous action, which actions need approval, who approves, what the daily spend ceiling is per agent.
  • Your model gateway. Register it as the provider endpoint and every call routes through it; your model selection, cost and latency policies apply unchanged.

Bringing an existing script across

Take the most common in-house artefact: a scheduled rightsizing job that reads CPU and memory utilisation from Prometheus, writes a report, and leaves a human to apply the changes. Here is how it moves.

  1. Install the control plane on a Kubernetes cluster in your own account with the Helm chart. Add a cluster with a second Helm install of the per-cluster agent. Point it at Prometheus with a read-only credential.
  2. Wrap the script as a workflow step. The existing container or script becomes a deterministic step. Nothing in it changes.
  3. Replace the schedule with a trigger and let the FinOps agent's continuous utilisation signal decide when the step runs, instead of a cron expression.
  4. Add the closing step the script never had: a pull request against your infrastructure repository with the proposed limits and the evidence behind them, behind the approval policy you set for that environment.
  5. Let memory take over. The next run knows which recommendations were accepted, which were rejected and why, and adjusts.

A Slack alert handler follows the same path. Its logic becomes a step, alert ingestion comes from the platform's Prometheus and New Relic integrations instead of your webhook receiver, and triage, deduplication and dependency-aware root cause are added in front of it rather than written by you.

Run it alongside what you have

Do not migrate on faith. Run NudgeBee next to your current system on one cluster for two weeks and compare.

Week one is read-only. Both systems see the same alerts. Measure how many reach a human after triage, how long the first root-cause analysis takes on critical alerts, and how often the two systems disagree on cause. Compare model spend, since both can route through the same gateway.

Week two switches on pull requests and guarded actions for the environment you chose. Measure the share of proposed changes that get merged and the time from alert to merged fix.

If your in-house system wins, you have learned something about your build and lost two weeks. If it does not, you have a migration plan with numbers attached.

Bottom line: this is the cheapest way to find out whether the in-house platform is ahead or behind, and it does not require anyone to admit anything.

When the enterprise layer earns its keep

Most of the platform is open source and stays that way: the agents, the integrations, troubleshooting, optimisation and the automation builder. Teams run it in production on the open-source version alone.

The enterprise licence adds the parts that matter once the agent fleet is large, the estate is multi-tenant or the organisation is regulated: the multi-tier memory layer across tenants and business units, the application-aware model router that picks models per step on cost and accuracy, model certification against each new release so your evals are not the first line of defence, and a support contract with people on the other end.

Start on open source. Move when the memory layer or the model churn becomes a line on someone's job description.

Bottom line: the licence buys back the two engineering roles the core would otherwise need. If the fleet is small, keep the money.

Why this compounds

An in-house platform grows as fast as the engineers assigned to it. A shared one grows on two fronts at once.

The first is memory. Every incident the agents work makes the next one cheaper and more accurate, because the facts, patterns, decisions and corrections are kept and reused. Your edge gets better without your team touching it.

The second is the platform itself. Every release adds skills, tools, agents and integrations, and your existing workflows inherit them. The upgrade pre-check that did not exist when you installed shows up and uses the same approval path you already configured. Your two platform engineers did not write it, and they did not have to.

So, not build versus buy. Keep what you built, move it onto a core that keeps learning and keeps growing, and spend the engineers on the part only you can do.

Frequently Asked Questions

What is NudgeBee OSS?
It is the open-source core of an agentic operations platform: always-on orchestration, structured memory and a service dependency graph, model routing, the integration layer, governance and cost controls. You run it in your own environment and build your workflows, agents and policies on top.
Can you run agentic SRE on open source?
Yes. The agents, integrations, troubleshooting, optimisation and the automation builder are open source, and teams run them in production on that alone. The enterprise licence is for large fleets, multi-tenant estates and regulated organisations.
We have two years of work in our in-house system. Does any of it survive?
All of the edge does: scripts, runbooks, prompts, policies and the knowledge. What you retire is the plumbing underneath.
Does NudgeBee replace our observability stack?
No. It queries Prometheus, New Relic, Datadog, Elasticsearch and the cloud APIs on demand and stores only insights and evidence, never raw telemetry.
Can we keep our own model gateway and our own models?
Yes. Any OpenAI-compatible endpoint is a provider; assign models per tier or per agent.
Where do we start?
Install the open-source control plane, connect one cluster, bring one script across, and run the two-week comparison above.
